# 流量监控版本发布

用于 `whoarei/traffic-monitor`。本技能随项目维护，以下文件路径均相对仓库根目录。发布以确定版本号、说明更新内容和完成 GitHub Release 为核心。

## 先确定更新内容和版本号

1. 读取 `app/version.py`、`CHANGELOG.md`、Git 状态、最近已发布版本及其标签到待发布代码的差异。更新点包含本次拟纳入的相关已提交与未提交修改，不只看最后一个提交。
2. **用户没有指定本次版本号时，必须先列出主要更新点，再给出候选 `x.y.z` 版本号及简短理由，向用户确认。** 提问同时说明当前 / 最近发布版本、拟发布内容和候选版本，让用户一次确认这两个事项。例如：“上次发布为 1.5.1；本次增加亮白主题、主题切换及选择记忆。建议发布 1.6.0，作为兼容的功能更新。这次按这些内容发布 1.6.0 吗？”示例版本不是默认值。
3. 等待明确答复后再修改版本、创建发布提交或标签、推送发布标签。不能自行递增，也不能把沉默或等待超时当成确认。用户已明确授权自行决定版本号时，按授权选择并说明依据。
4. 用户已在本次请求或当前对话中明确指定 / 确认目标版本时，沿用该决定，不重复询问。依据实际差异简要说明更新内容；只在发布范围仍有实质歧义时集中澄清。历史发布使用过的版本号不代表本次选择。

版本格式为无多余前导零的稳定版本 `x.y.z`，Git 标签为 `vX.Y.Z`。已发布的版本不覆盖；遇到重复版本时，说明现有状态并请用户明确目标。

## 发布

1. 更新 `app/version.py`。同步网页中的当前版本显示和静态资源版本参数，按需同步 README 当前安装文件名及文档适用版本；不批量改写历史版本或测试夹具。
2. 将已确定的更新内容写入 `CHANGELOG.md` 的 `## X.Y.Z · YYYY-MM-DD` 条目。发布签名脚本从该条目获取在线升级说明。Release 说明也使用本次更新点，避免只有通用附件介绍或提交标题。
3. 确认 `origin` 对应目标仓库，只提交本次发布相关内容，推送发布提交并创建、推送指向该提交的新注释标签 `vX.Y.Z`。不混入私人配置、运行数据或无关改动。
4. 使用现有 `.github/workflows/ci-release.yml` 生成 deb、签名清单和 GitHub Release。跟踪该标签的发布任务直到完成，不额外手工打包、创建重复 Release 或覆盖已公开附件。若需补充 Release 说明，使用确认后的更新内容；多行正文通过文件传给 `gh release edit --notes-file`。
5. 简要返回版本号、主要更新点和 Release 链接。失败时说明阻塞发布的具体原因，不把未完成的发布报告为成功。

## 保持发布流程轻量

- 不额外安排单元测试、浏览器回归、安装演练、下载验签、服务器验收或验收报告，也不为了发布新增测试或验证脚本。
- 现有 CI 自动执行的构建与检查沿用工作流，不要求本地重复执行；不因本技能而修改 CI。CI 失败时只处理阻塞发布的问题。
- 发布任务默认到 GitHub Release 完成为止；服务器部署按用户另外明确的要求执行。
- 创建或修改本技能本身不等于要求发布应用，不修改应用版本或创建发布标签。

需要了解现有发布机制时，按需读取项目的 `docs/releasing.md`；用户本次明确的流程要求优先。
